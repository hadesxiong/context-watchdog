# 文档索引

本目录是 ContextWatchdog 的仓库文档。每份文档单一职责，并各自绑定「什么时候必须
更新它」——改了对应的东西却没动文档，就是欠账。这份索引存在的目的：让「该改哪份
文档」在改代码的当下就能查到，而不是等它烂掉再考古。

```
docs/
├── README.md        ← 本文件：文档定位与更新触发
├── spec.md          # 技术真相源（§ 级结构，面向开发者与技术评审）
├── test-cases.md    # 手动验收用例与通过判据
├── releasing.md     # 发布操作手册（顺序 / tag / 商店提交 / 素材）
└── design/          # 设计决策与后续线（防御性公开，详见其 README）
```

## 文档清单与更新触发

| 文档 | 定位 | 何时必须更新 |
|------|------|--------------|
| [`spec.md`](spec.md) | 技术真相源：功能矩阵、架构、检测管线、规则与区域校验、档案、权限与 CSP、存储、构建、测试地图、已知限制 | 代码改变了「系统怎么工作」的任何时刻——与代码同一次提交改；数字基线（测试数等）随事实变化更新 |
| [`test-cases.md`](test-cases.md) | 手动验收用例与逐条通过判据 | 新增或变更**自动化测不到**的用户可见行为（视觉、权限弹窗、真实下载、真机交互）时 |
| [`releasing.md`](releasing.md) | 发布操作手册：部署顺序、tag、Release 附件、商店提交、素材清单 | 发布链任一环节变化（新渠道、素材要求、顺序调整、脚本增删）时 |
| [`design/`](design/) | 设计决策与后续迭代线，**有意随代码公开**（防御性公开，构成 prior art） | 立项新设计/新决策线时新增一份；决策被推翻时在原文标注结局，不删历史 |
| [`../CHANGELOG.md`](../CHANGELOG.md) | 实现轮次与结案记录（按时间倒序，压缩版） | 每完成一个可验收轮次归档一条；真机验收发现的缺陷修复也要记 |
| [`../TODO.md`](../TODO.md) | 当前状态、挂账项与回归命令基线 | 每次验收/清账后同步；基线数字（测试数、探针数）随事实更新 |
| [`../README.md`](../README.md) | 门面：简介、快速开始、可核验隐私表、数据流、文档地图 | 面向用户的事实变化时；**不放细节**——细节一律链向本目录，避免双份维护 |
| 落地页 `/changelog/`（`apps/site/src/i18n/`） | 面向用户的双语更新记录，只列已发布版本 | 商店过审/新版本发布时追加条目（zh/en 词典原子同步） |

## 跨文档联动（改 A 别忘 B）

- **改行为**：`spec.md`（怎么工作）→ `test-cases.md`（怎么验收）→ `CHANGELOG.md`
  （归档结案）→ 若用户可感知，落地页 i18n 文案同步；
- **改版本号**：唯一真相源是 `packages/extension/src/manifest.json`，
  其余位置由 `npm run check:versions` 强制对齐，不手工散改；
- **改发布流程**：`releasing.md` → 若影响商店审核口径，同步落地页 `/privacy/`
  与 README 的隐私表（审核会拿两处对照）；
- **README 与 spec 的边界**：README 只放门面与链接。2026-10-21 曾把 README 中
  约六成与 spec 重叠的架构细节整体并入 spec，别把它们搬回去。
